## Historical implementation outcome

A non-technical merchant can persist a business goal, industry, and first website bot in the current implementation. The server fixes the current launch channel to website, recommends a product Studio, derives progress from durable product evidence, and keeps support available throughout setup. These stored preferences must be adapted behind the approved package-first, role-guided experience; they must not place business-goal selection before bot and package selection.

## Schema and API impact

- Migration `0089_goal_first_onboarding` stores `first_product` as `flowbot`, `ai_chat`, or `voice`.
- `launch_channel` is constrained to `website` for this release train.
- `PATCH /tenant/onboarding` accepts the business goal, industry, and first product. It does not accept a channel authority from the browser.
- Existing product subscription and entitlement records remain the authority for access and readiness.

## Security and privacy

- All onboarding reads and writes use authenticated `TenantContext` and forced RLS.
- The first-product preference cannot activate a product or grant an entitlement.
- Cross-tenant preference substitution is covered by the tenant repository integration suite.
- Support context includes only an admitted workspace path and optional safe diagnostic code. It does not include credentials or provider details.

## Migration and rollback

- Forward migration adds nullable preference fields and a completeness constraint. Existing tenants remain valid until preferences are saved.
- Before production application, rollback is removal of migration `0089` from the unreleased migration train.
- After production application, do not drop preference evidence. Roll back application traffic to code that ignores the new nullable fields, then use a separately reviewed compensating migration if removal is still required.
- Migration `0088` support records are durable customer communications. Rollback disables support creation and replies at the application boundary but retains tickets, messages, and audit evidence.

## Verification

- Migration invariants require every preference field and the website-only constraint.
- Unit tests cover server-derived onboarding order and next actions.
- PostgreSQL integration tests prove tenant-scoped preference writes and unchanged neighboring tenants.
- The full clean PostgreSQL 16 suite applies all 90 migrations and exercises support, onboarding, RLS, bot runtimes, billing, privacy, recovery, and legacy migration rehearsal.

## Remaining acceptance

- Named Thai merchant usability acceptance is external evidence and cannot be fabricated by engineering.
